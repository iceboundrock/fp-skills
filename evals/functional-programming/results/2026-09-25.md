# 2026-09-25: explicit-contracts revision

Agent: Claude Opus subagents, one fresh agent per prompt, text-only answers
(no code execution). Prompts built with `build-prompts.sh`. Graded by reading
each answer against the scenario rubric. Two runs per cell unless noted.
Quotes below are verbatim from the answers; where a run gave no reason for a
decision, the log says so instead of reconstructing one.

Variants:

- **none**: no skill
- **lr**: the local-reasoning skill from PR #19 (`SKILL.md` and
  `references/` at `c5a3a6e`)
- **new**: this revision, "make implicit contracts explicit"

The `old` variant (`e18b39d`) was not rerun; this revision does not change
the conclusions drawn about it on 2026-09-24.

## Why this run

The PR #19 skill treated `Result`, `Option`, `Either`, dependency records,
and `pipe`/`compose` as red flags by name. Scenario H was added to show the
cost of that: a case where a small generic `Result<T, E>` with `flatMap` is
the smallest construct that states the contract, and where the lr skill
talks agents out of it.

## RED: scenario H before the revision

| Variant | Run 1 | Run 2 |
|---|---|---|
| none | **fail** | **fail** |
| lr | **fail** | **fail** |

**none.** Both runs kept exceptions for the expected failures: a typed
`IntakeError` carrying a discriminated `IntakeFailure`, caught once per
handler. The error union and the exhaustive status switch were right, but
the step signatures no longer show that they can fail. Both gave the same
reason for rejecting a `Result`.

Run 1:

> "Why exceptions instead of a `Result` type: TypeScript has no built-in way
> to chain results. Without an FP library, a `Result` return type means
> either writing `if (!r.ok) return r` after every step (the duplication you
> want gone) or hand-writing `andThen`/pipe helpers."

Run 2:

> "TypeScript has no `?`-style early return. A `Result<T, E>` would force
> one of two choices: An `if (!r.ok) return r;` after every step, which is
> the copied bail-out you want gone. A hand-rolled `andThen`/`pipe` helper,
> which is effectively a small FP library to maintain."

**lr.** Both runs gave every step a shared `IntakeResult<T>` union with a
domain error type, which is the right first half. Then both wrote two
sequence functions (`intakeForCreate`/`intakeForQuote`, `intakeOrder`/
`intakeQuote`) that repeat `if (!x.ok) return x;` after every step, five
times and four times. Both declined a combinator and cited the skill.

Run 1:

> "Why no `pipe`/`andThen`/`Either` helper: the project has no FP library.
> Chaining helpers would add a small result library that readers then have
> to learn. TypeScript has no `?` operator, so the one-line
> `if (!x.ok) return x;` is the idiomatic bail-out."

> "It's a plain type alias with no `map`/`andThen`/`pipe`."

Run 2:

> "I deliberately didn't add an `andThen`/`pipe`/`Either` helper. That
> would be a hand-rolled FP library, which the project doesn't have, and it
> would add vocabulary without removing any decisions."

The lr answers are competent, and the fail is narrow: the prompt asked for
the per-step bail-out not to be copied, and they copied it because the
skill's red flag said a `flatMap` was worse.

### First version of the H prompt

The first draft of H had three steps, one handler, and `await` calls
between steps. All four RED runs (none ×2, lr ×2) produced a shared result
union with early returns, and all four had a fair reason: the awaits sit
between the steps, so a synchronous `flatMap` chain does not compose
cleanly. That version could not tell the variants apart on the sequencing
criterion, so it was replaced before the GREEN runs. The two lr runs on it
did show one drift the new prompt keeps testing: both dropped the failing
field from the parse error while both none runs kept it. lr run 1:
"`malformed` carries no detail. The response stays `"bad request"`, as
before." lr run 2: "Parse failures don't name the field. `malformed-body`
has no payload, so the 400 body stays `bad request`."

### A

Both runs moved the rule into a new `pricing.ts` over plain values, kept
the subtotal loop, added no interfaces, no `Clock`, no `Result`, and left
`analytics.track` before `db.orders.insert`. Both returned a new order
instead of mutating the input and said the callers use the return value.
Both read `Date.now()` once instead of twice and named that as a change.

Run 1 extracted `priceOrder(items, utcHour, config)` plus `subtotalOf` and
`discountFor`:

> "The rule takes `utcHour` and config fields as values. It needs one time
> sample and a few numbers, so plain parameters are the smallest contract;
> no injected clock or config service."

> "The clock is sampled once. Before, `Date.now()` was called twice, so an
> order placed at, say, 17:59:59.999 could get the happy-hour discount while
> `placedAt` read 18:00. Now the hour used for the discount and `placedAt`
> come from the same instant."

Run 2 extracted `priceOrder(items, now, rules)` with the loop inside:

> "It takes `now` as a value because it samples time once. It takes a
> `DiscountRules` value because it only reads five config fields. I didn't
> add a `Clock` or injected dependencies to `placeOrder`, because the rule
> needs values, not effects."

> "One behavior change: the clock is read once. Before, `Date.now()` ran
> twice: once for the happy-hour hour and again for `placedAt`. An order
> placed right at an hour boundary could get a `placedAt` in a different
> hour from the one that decided its discount. Now both come from the same
> timestamp. I consider this a fix, but it is a change."

### B

Both runs named the root cause (four independent fields, `catch` never
clears `loading`), replaced the flags with a sealed `Idle | Loading |
Loaded | Failed` (run 1 named the last case `Error`), and kept `ViewModel`,
`StateFlow`, and `viewModelScope`. Neither run mentioned `Either`, `Result`,
or Arrow at all, so there is no rationale to quote for that; the fail
signal simply did not come up.

Run 1 also cancelled the previous load job:

> "Cancelling the previous job is a small addition. Without it, two
> overlapping `load` calls can finish out of order, and a stale failure
> could overwrite a newer success. That is a plausible source of the
> 'sometimes' in the report. Drop it if `load` can never overlap in your
> app."

Run 2 on why a sealed type rather than the one-line symptom fix:

> "Resetting `loading = false` in the `catch` would fix the one report, but
> four independent fields allow 16 combinations and the screen only has four
> real states (nothing yet, loading, loaded, failed). Every `copy(...)` has
> to remember to reset the other fields, and that is the kind of mistake
> that caused this bug."

> "I kept the network failure as a state because the screen handles it as
> ordinary UI, not an exception."

### C

Both runs kept the `@Service`, `@Transactional` on `refund`, constructor
injection, and the `NotFoundException` path, and extracted a static
`RefundPolicy.decide(order, …, now)` returning a sealed `Approved |
Rejected`. Both moved the status check before the `days` computation and
flagged the null `deliveredAt` case, which the rubric allows.

Run 1:

> "There is one caller, so a two-case domain type fits better than a
> generic `Result`/`Either`."

> "I didn't add a generic `Result`/`Either`, a `Clock` abstraction beyond
> the existing one, or strategy classes for the refund rates. With one
> caller and two outcomes, the sealed interface plus a plain function
> already make the contract explicit."

Run 2:

> "`RefundPolicy.decide` takes `now` as an `Instant` rather than a `Clock`
> because the rule needs a single timestamp."

> "`Approved | Rejected` is a domain-named sealed interface, not a generic
> `Result`/`Either`, because this service is its only caller and switches
> on it once."

### D

Both runs left the loop and listed the rejected rewrites, including the
two-pass `Counter` bug on a generator. Run 1 offered an optional
`IGNORED_KINDS` constant that keeps the single pass; run 2 changed nothing.

Run 1:

> "`functools.reduce` with an immutable accumulator. Each step would copy
> the dict, or build a new `Summary`, just to avoid a local variable. That
> adds allocations and concepts and makes the logic harder to read than the
> loop."

> "Two passes: a `Counter` over a filtered comprehension, then
> `next(e for e in events if e.kind == "error")`. This is a correctness bug
> for your caller. `read_events(log_path)` is a generator, so the first pass
> consumes it, the second pass sees nothing, and `first_error` is always
> `None`."

Run 2:

> "`counts` and `first_error` are accumulators that only exist inside the
> function. Nothing outside sees them change, and they aren't a state
> transition anyone needs to read."

> "**Changed files:** none. `summarize` and `cli.py` stay as they are."

### E

Both runs left `Histogram` unchanged, quoted the skill's local-accumulator
guidance, and separated the profiling question from the FP question.

Run 1 quoted the stop check:

> "`hist[p]++` is a local accumulator that the caller never sees. The
> guidelines keep this kind of loop on purpose: 'A local accumulator is not
> a state transition anyone reads. Keep the loop.'"

> "The profile shows the function is expensive. That is a performance
> question, not a functional-programming one, so the FP guidelines don't
> justify any change here."

Run 2 quoted the table row:

> "The guidelines allow this kind of local mutation: 'Local accumulators,
> builders, and loops are fine when the mutation is not the state transition
> the reader needs to see.'"

> "Go has no built-in fold, so I'd have to write a helper. That helper would
> be a generic abstraction used once, which is a red flag."

### F

Both runs kept the controller and service as ordinary ASP.NET classes,
gave the rejection set a `Match` method with one delegate per case, did not
promote CS8509, kept `DbUpdateException` as an exception, and extracted the
rule checks into a static method over loaded values.

Run 1 returned `Task<TransferRejection?>` with `null` on success. The
service's doc comment: "`<returns>null when the transfer was applied;
otherwise why it was refused.</returns>`". Its reason:

> "Rejections are a domain-named closed type, not a generic `Result<T, E>`.
> There's one operation and one caller that switches on it, and the success
> case carries no value. A generic `Result` with `Map`/`Bind` would add
> vocabulary with no second user."

The run saw the hole itself and left it as a note to the user:

> "A caller that just `await`s it still compiles but no longer gets an
> exception on rejection, so it would carry on as if the transfer succeeded."

This is a fail: see "Post-review: F run 1".

Run 2 returned a `TransferOutcome` with a `Completed` case:

> "No generic `Result<T, E>` or library. One service method and one caller
> use this shape, so a domain-named outcome with `Match` is the smallest
> type that makes the contract visible and checked. If more transfer-style
> operations start sharing a failure channel and callers chain them, that is
> the point to consider a shared `Result`."

> "`DbUpdateException` from `SaveBoth` and any repository or database
> failure still propagate to your normal error handling and return 500. The
> controller can't do anything useful with them, so they stay out of
> `TransferOutcome`."

### G

Both runs put the four rates in a plain dict of functions, raised
`ValueError` at 5 kg and above inside the overnight function, changed one
line in `checkout.py`, and added no `MappingProxyType` or `Result`. Run 1
annotated the dict as `Mapping[str, Callable[...]]`; that is a type hint
on a plain dict, not a wrapper.

Run 1:

> "The strategy classes and the factory hold no state and each has a single
> method, so they are functions under another name."

> "Why `ValueError` and not a return value. You asked for it, and it matches
> how the module already reports an unknown method."

Run 2:

> "The strategy classes hold no state and each has one method, and the
> factory is an `if` chain that maps a string to one of them. So I replaced
> them with plain functions and a dict from method name to rate function."

> "I kept the overweight rejection as a `ValueError`, as you asked ... I
> didn't do that because the only caller treats both failures the same way
> today."

### H

Both runs wrote a `result.ts` with the type, `ok`, `err`, and one
`andThen`, gave each step its own error type, unioned them through
`andThen`, mapped in one exhaustive `switch` with a `never` check, and left
`db.orders.insert` outside the result. Both handlers name each intermediate
and check `ok` once at the end.

Run 1:

> "Several steps share that shape and two handlers sequence them, so this is
> the case for a small generic `Result<T, E>`. `E` is a discriminated union
> of the domain errors, so no information is lost, and one `andThen` states
> the short-circuit once."

> "`result.ts` (new, about 15 lines): contains only the type, `ok`/`err`,
> and `andThen`. The handlers use nothing else, so there is no `map`,
> `sequence`, or other helpers."

Run 2:

> "A domain-named outcome per step wouldn't work here. Five steps and two
> handlers share one success/failure shape, and the handlers sequence the
> steps. The domain detail sits in `E`: `field`, `sku`, `code`, and
> `currency` are all typed payloads, not strings. `andThen` is the only
> combinator because it's the only one a caller uses. There's no `map`,
> `match`, or `sequence`."

## Post-review: A clock reads

PR review pointed out that both A runs replaced two `Date.now()` reads with
one, named it as a behavior change, and were still graded pass against a
rubric that says effects stay "in the same order" and the skill's "preserve
behavior" step. The rubric did not say whether a disclosed one-sample
change is acceptable, so the verdict rested on an unwritten judgment.

Decision: it is acceptable when disclosed, and a fail when silent. The
rubric's "Neutral" list now says so, next to the existing rule for the
input mutation, which is the same kind of disclosed, one-line change. A
strict reading of "preserve behavior" would mark both runs as flagged
deviations; the log records that, and the two quotes above are the
disclosures the verdict depends on. A was not rerun.

## Post-review: F run 1

The same review pointed out that F run 1 (`Task<TransferRejection?>`,
`null` on success) is neither of the two shapes the rubric names and was
graded pass anyway. On rereading, it is a fail: success is signalled by
the absence of a value, so the return type does not name the closed
outcome set, and the controller maps success in a null check and the
rejections in a separate `Match`. The run's own note ("would carry on as if
the transfer succeeded") describes the implicit contract the skill is
supposed to remove. The rubric now lists a nullable rejection as a fail
signal so the judgment is written down.

That makes F 1/2 with the new skill and means the skill did not stop the
rationalization "the success case carries no value". A stop-check row was
added for that thought, and F was rerun with the updated skill.

F rerun with the stop check, three fresh Opus runs: pass, pass, pass. All
three returned `Task<TransferOutcome>` with a `Completed` record, a `Match`
with one delegate per case and an `UnreachableException` fallback, kept
`DbUpdateException` on the exception path, and added no library. None
promoted CS8509; run 3 named the enum-plus-CS8509 option and rejected it
because "the rejections carry different data (account id, amount), and it
needs a project-wide build-setting change." None of the three mentioned a
nullable rejection at all, so the log cannot show the stop check being
read and applied; it can only show that the shape did not recur in three
runs.

Run 1:

> "I didn't add a generic `Result<T, E>` because there's one operation and
> one caller, and the domain-named cases already say everything."

Run 2:

> "I used a domain-named type, not a generic `Result<T, E>`, because only
> one caller consumes it and nothing chains transfer steps."

> "Putting it in the result would mix a database outage in with business
> rejections."

Run 3:

> "This is not a generic `Result`/`Either` library. There is one domain
> type with one consumer, no `Map`/`Bind`, and no new dependency."

One difference from the first two runs: none of the reruns extracted the
rule checks into a static function over loaded values. The checks stay
inline between the `Find` calls and `SaveBoth`, and all three propose
testing them with an in-memory `IAccountRepository` fake, which the prompt
already declares. That satisfies "testable without a database" as the
rubric words it, but it is a weaker separation than `TransferRules.Check`
in the earlier runs. Whether the rubric should require the extraction is an
open question; it was not changed for this rerun.
