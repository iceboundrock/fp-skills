## Why this run

PR #23's recovery review (2026-10-22, not published) found that eval agents
started inside this repository load its `CLAUDE.md` and `AGENTS.md`. Since
`11ac3c4`, `AGENTS.md` says what scenario H rewards: "its scenario H stops
over-correction (refusing a shared `Result` with `flatMap` where several
steps share a failure channel)". The review reported clean H runs (none
pass ×2, lr fail ×2, new pass ×2) and said lr passes ×2 when the
instructions are loaded. Its clean-run outputs have since been deleted.
This log checks the isolation claim against transcripts, reruns H under a
checked configuration, and records what the earlier logs' runs had in
context.

## H results

| Variant | Run 1 | Run 2 |
|---|---|---|
| none | pass | pass |
| lr | **fail** | **fail** |
| new | pass | pass |

**none.** Both runs wrote a `Result` with `ok`, `err`, and a chaining
helper (run 1 a `chain()` object, run 2 a `Pipeline` class, each with one
`andThen`). Each step gets its own error type, the chain unions them, one
`switch` with a `never` check maps them, and the insert stays outside.

> "`chain(...).andThen(...)` skips the remaining steps after the first
> failure, so the "check and return early" code isn't copied after every
> step."

> "`Pipeline.andThen` stops at the first failure, so neither handler repeats
> the bail-out code. It's about 15 lines of plain TypeScript and adds no
> dependency."

**lr.** Both runs gave every step a shared `IntakeResult<T>` with a
domain failure union, an exhaustive `switch`, and the insert outside. Then
both wrote two pure sequence functions that repeat `if (!x.ok) return x;`
after each step, four times and three times. That is the copied bail-out
H fails. Moving the sequences into functions over the loaded tables is
neutral. Both cite the lr skill's rule against a home-made helper.

Run 1:

> "TypeScript already has this kind of union, so I didn't add a library or
> a home-made `Result`/`pipe` helper."

> "Removing even that line would mean either throwing for expected outcomes
> again or building a home-made chaining helper, and I think both are worse
> than one plain line."

Run 2:

> "To remove it I'd need an `andThen`/`pipe` helper (a homemade FP library)
> or steps that throw, and both seemed worse than one line each."

**new.** Both runs wrote a `Result` with `ok`, `err`, and `flatMap`, named
each intermediate, checked `ok` once at the end, and mapped failures in one
exhaustive `switch`, with the insert outside. Run 1 gives each step its own
error type; run 2 uses the full `IntakeError` for every step.

> "`result.ts` has just the type, `ok`, `err` and `flatMap`; it's plain
> TypeScript with no new dependency."

> "all five steps fail the same way and both handlers chain them, so one
> `Result` and one `flatMap` lets the stop-at-first-failure rule be written
> once."

All six narrowed the `normalizeLines` catch, which H lists as neutral.
none run 1 also moved the negative-quantity check ahead of the merge ("I
assumed you can check for negative quantities on the input lines before
merging"), which the rubric does not grade.

## What H is for

The owner decided on 2026-10-23 that H is a regression guard against
#19's over-correction: refusing a shared expected-failure type or a
sequencing helper because it looks like an FP abstraction. A `none` pass
is acceptable and is reported as observed. H's original design, and the
2026-09-25 RED section, expected `none` to fail too. That expectation is
not met in isolation; it is recorded here, not rewritten, and the rubric
is unchanged. H does not show that the new skill improves on no skill for
this scenario.

## Scenario A clock check

A Node 24 script compared A's original `placeOrder`, the shell all five
passing A runs used (`computePricing(order.items, Date.now(), CONFIG)`),
and a shell that computes the subtotal before the first read. Each clock
is fully controlled by the test.

| Clock | Original | First read before the loop | Subtotal, then first read |
|---|---|---|---|
| Fresh per-read stub (17:59:59.999, then 18:00:00.000), 3 items | discount 15 | 15 | 15 |
| Deterministic, +1 ms per item read, from 17:59:59.997, 5 items | 50 (bulk) | **25 (happy hour)** | 50 |
| One stub shared by a call with non-iterable `items`, then a valid call | 0 reads on the throw; next call discount 5 | **1 read on the throw; next call discount 0** | 0 reads; 5 |

Every version reads the clock twice and then tracks and inserts, as the
original does; only the position of the first read differs. The 2026-09-25
log uses these results to limit its clock-equivalence wording.

## Limits

- Two runs per cell on one model. 2 of 2 is not a reliable rate, and more
  samples could flip a cell. None of the six was a close call on the
  rubric.
- Only H ran in isolation. Every other verdict in the 2026-09-25 log ran
  with the repository's `AGENTS.md` in context, or probably did. The PR's
  `AGENTS.md`
  names "`reduce` replacing loops, a generic `Result` for one operation,
  interfaces added only for tests", which bears on D, F, C, and A's
  test-only interfaces. It says nothing about A's clock reads or F's rule
  extraction. #20 covers isolated baselines.
- The grader ran the experiment and knew the recovery's reported results
  before grading.
- The default Claude Code system prompt and the three built-in plugins were
  present in every run. Another harness may behave differently.
- The raw outputs (six `stream-json` files, the extracted answers, the
  probes, and the clock script) are in this session's scratchpad, not in the
  repository, and will not last.
