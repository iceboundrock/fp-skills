## Why this run

The PR #19 skill treated `Result`, `Option`, `Either`, dependency records,
and `pipe`/`compose` as red flags by name. Scenario H was added to show the
cost of that: a case where a small generic `Result<T, E>` with `flatMap` is
the smallest construct that states the contract, and where the lr skill
talks agents out of it.

### First version of the H prompt

The first draft of H had three steps, one handler, and `await` calls
between steps. All four RED runs (none ×2, lr ×2) produced a shared result
union with early returns, and all four had a fair reason: the awaits sit
between the steps, so a synchronous `flatMap` chain does not compose
cleanly. That version could not tell the variants apart on the sequencing
criterion, so it was replaced before the GREEN runs. The two lr runs on it

## Post-review: A clock reads

PR review pointed out that both A runs replaced two `Date.now()` reads with
one, named it as a behavior change, and were still graded pass against a
rubric that says effects stay "in the same order" and the skill's "preserve
behavior" step. The first response was to accept a disclosed single sample
and fail a silent one, on the model of the input-mutation rule in the
rubric's Neutral list.

A second review rejected that: disclosure does not make the change
behavior-preserving. At an hour boundary the original code can grant the
discount in one hour and stamp `placedAt` in the next, one sample changes
that observable result, and the task asked for a refactor and tests, not
that change. The rubric now requires both reads ("read once for the
happy-hour check and again for `placedAt`, as before"), lists the collapse
as a fail signal whether or not the answer says so, and drops the Neutral
bullet. Both GREEN A runs are regraded as fail; the quotes under "A" above
are where each run made the change.

## Post-review: one criterion for a generic `Result`

The fifth review found the guard on a generic `Result` worded three ways.
The skill's legitimacy paragraph asked for several operations that share
the shape and callers that sequence them. The domain-outcome sentence, the
stop-check row, the list of performative uses, the C# trap, and
`AGENTS.md` counted callers ("one caller switches on them", "a single call
site", "only one controller switches on", "a generic `Result` at one call
site"). F's fail signal counted sequencing ("nothing sequences transfer
steps"). F and H
each satisfy all three wordings at once, so no scenario separates them;
they disagree on one operation that several callers switch on without
chaining it. F's header had picked the caller reading ("The fail is for the
missing second caller, not for the name"), which the legitimacy paragraph
does not support.

The review probed that case: F's prompt with a second caller,
`StandingOrderJob.RunDue`, that catches the same four exceptions. Both of
its runs on `0bc8748` chose a domain-named outcome and gave the number of
operations as the reason, so agents already read the legitimacy
paragraph's criterion; the risk was to rubrics written from F's header. `85750e2`
states that criterion everywhere: a domain-named outcome fits one
operation, however many callers switch on it, and a generic `Result` fits
several operations that callers sequence. The domain-outcome sentence, the
legitimacy paragraph ("The number of callers is not a reason"), the
stop-check row, the review question, the TypeScript, Kotlin, Java, and C#
entries, F's header and fail signal, `AGENTS.md`, and the evals README now
say the same.

The same commit makes three smaller changes from the review:

- The skill's only generic-`Result` example showed one function,
  `validateTransfer`, with F's rejections as its errors: the single-operation
  shape the guard rejects, in the domain of the scenario that tests it. It
  now adds a `parseTransfer` step, a `flatMap`, and a `checkTransfer` that
  sequences the two. The review suggested a `checkLimits` step. A parse step
  was used instead because a limits check is one of F's rule checks, and an
  example that splits them into chained steps could pull F answers toward
  the generic `Result` F fails. The F reruns below check that.
- F's escape hatch for a project's existing result type now requires the
  answer to reference it without defining it. An answer that defines
  `Result<T, E>` is introducing it, whatever it says it assumes.
- The Go entry said generics give no `?`-style sequencing, which is the
  argument the skill answers for TypeScript ("A `flatMap` is a few lines").
  The review proposed the Go-specific reason that methods cannot declare
  type parameters, so `r.FlatMap(f)` cannot be written. Go 1.27 (released
  2026-08-19) allows type parameters on methods of concrete types, so that
  reason no longer holds. The entry now gives one that does not depend on
  the version: `(T, error)` already puts the failure in the signature, every
  library returns it, and a generic `Result[T]` needs a conversion at each
  library call without making anything more explicit.

## Post-review: A's first clock read before the subtotal

The sixth and seventh reviews found that A run 3 on `2e725b2` moved the
first `Date.now()` ahead of the subtotal loop and called that unobservable
("Adding up the subtotal has no side effects, so nothing observable
changes"). The review reproduced a different discount with a clock that
advances in real time from 1 ms before 18:00 while a five-million-item loop
runs. The original samples hour 18 and gives no discount; the moved read
samples hour 17 and gives the happy-hour discount. The review recommended
regrading run 3 and having A require the first read after the subtotal.

The saved answers show that every passing A run in this log has this
shell, not only run 3. All three `2e725b2` runs and both `1c8aeca` runs
pass the items and the first read to the pure function:

```ts
const { discount, total } = computePricing(order.items, Date.now(), CONFIG);
order.discount = discount;
order.total = total;
order.placedAt = Date.now();
```

Run 3 is the only one that said the read moved. The sixth review's two A
runs, on `c950d9f`, computed the subtotal in the shell and read the clock
after it.

A script ran the original `placeOrder` and run 3's version under four
clocks:

| Clock | Original vs run 3 |
|---|---|
| A stub returning a fixed sequence of reads: 4 sequences, orders of 1, 3, and 1,000 items | Same order, same track and insert |
| Frozen at 17:59:59.999, as fake timers are until advanced | Same |
| Real time elapsed from 17:59:59.999, 3,000,000 items | Different discount, as the review found |
| Stub returning 17:59:59.999, then 18:00:00.000 | Same; the one-read collapse returns a different `placedAt` |

Under the real-time clock the original also differs from itself. Starting
the clock 30 ms before 18:00, the same order got the bulk discount on the
first call and the happy-hour discount after twenty warm-up calls, in 5 of
5 processes.

The verdicts stand. A protects which read decides what and the order of
the effects: the first read decides the hour, the second stamps
`placedAt`, then the track and the insert. Any clock a test can control
gets the same order back from both versions, while the collapse shows up
under a two-value stub. The review's clock measures how long the code
before the first read runs. That changes the original's own result
between a cold call and a warm one, so no refactor can be held to it. The
subtotal loop has no effect to keep in order. Requiring the read after the
loop would also fail the items form that A's first pass criterion allows,
which all five passing runs used. A's Neutral list now says this.

C draws the same line from the other side. Moving its status check ahead
of `days` fails because an undelivered order gets a different outcome.
Here no input does once the clock's values are fixed.

One difference does not depend on time. If `order.items` is not iterable,
the original throws before reading the clock, and run 3's version reads it
once first. Both throw the same `TypeError`, and neither tracks nor
inserts. Only a spy counting `Date.now()` calls would see the extra read,
and no value from it reaches the caller.

Run 3's sentence is still wrong as written. The first read does happen
earlier, by the loop's running time; what holds is that no test clock can
tell. The quote and the pass both stay.
